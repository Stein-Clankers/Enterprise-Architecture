# Archipelago PR review

Review the PR given in `$ARGUMENTS` (PR number; optional effort level, default `high`).

## 1. Establish context

- `gh pr view <n> --json title,body,baseRefName,headRefName` — read the description and note the base branch. **Stacked PRs: review only this PR's increment** (diff against its own base), never the whole stack at once.
- `gh issue view <linked-issue>` — extract the acceptance-criteria checklist. The PR body names the issue; if not, infer from the branch name (`feat/<issue#>-…`).
- **If the PR has been reviewed before, read that round's disposition first** — `gh pr view <n> --json comments` plus the follow-up issues it filed. On the #24 re-review, 10 of 15 candidates from the generic pass were already scoped into #33, #35, #38 and #39, several with the author's reasoning recorded on the PR. Re-reporting them would have re-litigated settled decisions and buried the two findings that mattered. List them as "already tracked" and move on; a deferral you disagree with is an argument to make once, explicitly, not a finding to re-raise.
- **A PR merged before its review is reviewed as a fix PR on `main`:** the verdict says what the fix PR carries, and the rest goes to follow-up issues. GitHub refuses `--request-changes` on your own PR, so post `--comment` with the verdict in the body.
- UI-touching PRs: read the relevant sections of `design/handoff/2026-08-inventory-factsheet-graph/README.md` (tokens, the screen being built) and compare against the reference screens in `screens/`. Fidelity is **high** — spacing, colors, and interaction states are normative.

## 2. Spec conformance (the project layer — this is what generic review can't do)

For every acceptance criterion: **met / not met / not verifiable from the diff** (say why, e.g. "needs a running browser — covered by e2e journey 3").

Where the diff touches them, verify the CLAUDE.md invariants:

- Canonical JSON determinism: sorted keys, stable IDs, byte-identical export→import→export (test must exist, not just code).
- Lifecycle **derived, never stored** — reject any stored phase field.
- Relationship properties first-class — reject demotion of edge data to element fields.
- All model mutations via the command stack — no direct store writes from UI code.
- Tokens are law: no color literals outside `src/styles/tokens.css`, zero border-radius, no shadows (exception: command palette), no runtime CDN/font fetches.
- Nothing leaves the browser except user-initiated downloads.
- **A declared ARIA widget role is a contract — check the behaviour, not the attribute.** Any component with `role="dialog"`/`aria-modal`, `role="menu"`, `role="listbox"` or `role="combobox"`: does focus *enter* the widget, is it *trapped* while open, is it *restored* to the trigger on close, and is the active item announced (`aria-activedescendant` with real option `id`s when focus stays in an input)? Lint (#40) catches the static half — a role on the wrong element, a missing required prop — and none of this half. Found in #24 (`role="menu"`, no keyboard) and #25 (`aria-modal` with no trap, `listbox` never announced). **Restoring focus to the opener goes nowhere when the dialog's action removes the opener:** #142's "Delete from model…" button lived in a panel the deletion unmounted, so focus fell to `<body>` and the canvas stopped taking keys. For each dialog action, check what it unmounts, and where focus should go instead.
- **A second call site of a data-safety path is a finding in itself.** When a PR reaches for `markSaved`, `replaceWorkspace`, `saveSnapshot` or a download, check whether an existing call site already does it — and whether this one kept its guards. #25 copied `Header.saveFile` and silently dropped its reader-role check. Prefer "collapse the two into one helper" over "fix the copy".

- **Grep the e2e journeys for the screen the PR touches, and treat a miss as a finding.** `tests/e2e/` runs the *built* bundle in a real browser, which is the only place workers, code-split chunks and the base path exist at all. #54 was a dependency graph that failed in every browser on six green checks, and the reason nothing caught it is that the graph had no journey — the harness had been built for precisely that risk and then never pointed at the screen. `grep -rn "<route or heading>" tests/e2e/` costs one command; if it returns nothing, the PR's browser-only failure modes are untested by construction.

- **The test behind an acceptance criterion must fail when the feature is removed** (now also a CLAUDE.md convention — it kept being broken by implementers, who do not read this file). A green test is not evidence. **Do not reason about it — break it:** delete the feature, or invert the condition, and run that one test. If it still passes, it is not covering the criterion. Recorded tells: one-sided bounds (`expect(n).toBeLessThan(150)` passes at 0); a setup that rebuilds the very thing whose caching it means to test (#27's `deps` test rerenders with a fresh workspace, so a whole new store busts the memo and `...deps` is never exercised); a test named for a case its setup skips, where **the giveaway is often a comment admitting it** (#27: "ArchiSurance Netherlands composes Back Office, so it does have one"); and assertions on the *opposite* branch (that same test asserts `getByRole('img')`, which only renders when the empty state does **not**). Found in #25, #26, and twice in #27.

  **When a criterion says "X updates live", check that a test asserts X's own value — not a sibling value rendered by the same component.** #24's health footer renders counts and completeness side by side; the live test asserted `29 elements · 47 relations` before and after a model change and left `health` to `>0` / `<=100`, so replacing `store.health()` with the constant `1` kept all 270 tests green. One component, two facts, one of them uncovered. Read the criterion's *noun* and grep the test file for it.

  **A criterion that is satisfiable by inspection is the one most likely to have no test.** If you can settle it by reading a file, you can assert it — and if nobody did, it regresses the first time someone edits that file. #24's "no layout shift when switching themes" was **met**: the dark block redefined only colours. Nothing proved it, and the theme test asserted `dataset.theme`, which passes just as happily with `--rowh: 30px` in the dark block. Where a criterion reduces to a property of a file, write the file test.

  **Asserting that a pure function returns a token is not asserting the token is rendered.** For any visual encoding behind a criterion — colour views, dimming, dashing, focus rings — check that a test reads it off the DOM. #28 asserted `colourOf`/`legendFor` as pure functions and legend *text*, so replacing `GraphNode`'s entire style object with `{width, height}` left all 33 graph tests green: the colour views and click-to-trace could ship with no visible effect at all. **A class name is not the encoding either:** jsdom applies no stylesheet, so a class asserted in a unit test proves only the selector, and the journey must read the computed style (`toHaveCSS`) against an unstyled sibling. #196 asserted its tree greying as `tree__row--greyed` in five unit tests and in its journey, and emptying the CSS rule left all of them green.

  **A fixture that hard-codes the expected answer is not a test.** #28's trace panel reads cost from the wrong place entirely (an element property, against ADR 0001), and its assertion passes only because the bundled demo XML happens to carry that exact string. When an assertion's expected value also appears in the fixture, check which one is the source of truth.

  **When a test's expected list repeats one value, ask what the consumer does with the equal values.** #229's own spacing test expected `Q1, Q1, Q1, Q1, Q2`, and nobody asked which phase four milestones in one quarter yield: since a date is reached on its period's first day, the site read Migrated before any cutover.

  **When a PR body ships a guard-removal table, re-run the rows whose guard has more than one predicate, and narrow rather than delete.** Deleting is what the author already did, and it proves only the weakest predicate. #228's table said `!touchesBlackout(d, addDays(d, freeze))` was caught, because deleting the call put a cutover *day* in a blackout. Narrowing it to `touchesBlackout(d, d)` left all 42 seeded-problem tests green on all seven seeds, so nothing pinned the freeze window.

- **Uncontrolled inputs plus a route parameter is a data-loss bug.** Any `defaultValue`/`defaultChecked` on a screen routed by `/:id` — and any sibling state such as an `editing` flag — check what happens when the id changes without a remount. #27 carried one element's name and documentation onto the next and committed them on blur. The fix under review should be `key={id}`, not a reset effect.

- **A parser option is a change to every value the parser returns.** When a PR changes the `XMLParser` options (`trimValues`, `removeNSPrefix`, `parseTagValue`, …), list how an *empty* element now arrives — `<x/>`, `<x> </x>`, `<x>\n</x>` — and grep every `!value`, `=== ''`, `list(…)` and `isRawNode` guard that relied on the old shape. #100 turned off trimming to stop silent text changes and, by the same stroke, made `<model> </model>` parse to `' '`: truthy, so an empty file imported as an ok model again, and `<bendpoint>\n</bendpoint>` fell through the very fix meant to keep it (#106 review). **Grep every `.filter(isNode)` that stands ahead of a count or a position too:** an empty element arrives as `''`, and dropping it there moves everything after it (#216's `<c/>` without `r` read `[1, 3]` for `[1, empty, 3]`). **When a finding says "grep every X", the disposition lists the grep's hits and what became of each:** #216's fix took the two instances the finding named and left the third, `cellXfs`, where a bare `<xf/>` shifts every style after it and a number reads as a date.

- **A ledger mark hoisted above a branch certifies the drop in the branch that neither keeps nor reports the value.** The readers' `Ledger` (#101) trusts every `use`/`text`/`whole` call, so for each mark in the diff, find the branches below it and check that *each* one stores the value or reports it. #110 marked a Label's `conceptRef` before an `if` whose reference branch kept nothing and reported nothing: the drop was silent, and the ledger now vouched for it. The same block marked the label read on a branch whose node holds no text. **Anything a mark *counts* or *decides* has the same problem one level up, because a reader marks before it skips:** `readElement`, `readNode` and friends mark their texts, and the caller finds the duplicate id afterwards. #114 tallied each text's `xml:lang` at mark time, and a probe with three skipped duplicates turned a German model French. For a tally fed by marks, list every later `skip` and every value read and then dropped (model-level properties, unused definitions, labels Archipelago writes itself), and check that each one is taken back.

- **A list of another tool's attributes is checked class by class against that tool's model, not as a flat set of names.** `javap` each class the reader maps, and diff its properties against what the reader reads, lists as known-unsupported, or ignores. #110 built Archi's undrawn display attributes from one flat string dump and missed that `DiagramModelConnection` also has `textAlignment`, which turned a real Archi setting from an info note into an "unread content" warning.

- **Evidence from another tool is asserted as that tool's number, not as agreement with our own geometry, and it goes through the path the screen uses.** A test titled "as Archi does" must compare against Archi's measured value. #116's group test checked the label against half of *Archipelago's own* tab height, which holds for any tab: tab height +20, 8 px off Archi, stayed green. It also rebuilt ViewDrawing's dispatch, so dropping the appearance on the real canvas path could not fail it. Look for a related trap: **one value decided in two places.** #117 picked a tabbed label's box in `labelBox` and its position through `defaultPosition`, so an explicit top and an absent one drew 3 px apart. Each looked right on its own. #119 converted a legacy type name for the reader, while the labeller of unread content still classified the raw name and called a renamed relationship an "element". Apply a conversion once, at the source, and have every consumer read the converted value. **The same holds for an order:** where the model stores an order and something else walks it, they must be the same order. #140's re-parent left a node at its old index in `view.nodes`, so `dropTarget`, walking the array, picked its parent while the drawing, painting in tree order, showed the child on top; and the node painted under its new siblings, where Archi appends it. Walk the order that is drawn, and keep the stored order equal to it.
- **A rule about what is drawn applies to everything that measures the drawing, not only to what paints it.** When a PR stops drawing something (hides, filters, collapses), grep every consumer of the same collection: hit-testing, selection, fit, extent, the mini-map, the export canvas. #155 hid connections a nesting shows in the drawing, the hit layer and the selection, and `drawingBounds` still counted their bend-points, so fit and the exported image kept room for a line nobody sees. Better still is one function that returns what is drawn, which every consumer calls.
- **State held per store outlives a workspace.** `replaceWorkspace` keeps the store, so anything keyed on it (a `WeakMap` on the store, a ref, a module cache) carries one workspace's data into the next. For each such piece of state, check what happens after Open file, and whether what it carries in brings its workspace-level declarations (`propertyTypes`, `tagGroups`) with it. #185's clipboard pasted another model's elements with Archi's same-model ` (copy)` suffix and without the typing of their properties.
- **Every control that writes has a reader case, and its test fails when the guard goes.** A route renders for a shared-folder reader (`role` is `'reader'` while `tabRole` is `'writer'`, ADR 0010), so for each control the PR adds that dispatches, delete its `readOnly`/`editable` guard and run `src/ui`. Then check that a mode the guard only keeps you from *entering* (an `editing` flag) cannot outlive a change of role. #192's model sheet copied the element sheet's `disabled={readOnly}` Edit button: deleting it on either sheet left every test green, and edit mode survives the role becoming reader (#195).
- **A default users see, switched off in the test harnesses, is a configuration no test runs.** When a PR turns a behaviour on for users and off in `setup()` or `tests/e2e/support.ts`, flip the harness default and run both suites once. Every failure must be an exact-value assertion, not a broken flow, and the review says so. #188 turned snapping on for users and off in both harnesses: flipped, 11 unit tests and 1 journey failed, all on landing pixels.
- **Porting another tool's rule means porting its predicate, not reusing ours.** "One value decided in two places" is about two consumers of one of *our* values; it is not a licence to swap in our approximation of the other tool's condition. #123 ported Archi's `FixDefaultSizesHandler` with the reader's own "unset" (absent, malformed or not positive), when Archi's is `== -1`. A 0-width group that Archi kept was grown to 430 × 140, and the summary over-counted. Read the predicate off the source, and probe the values our approximation adds (0, negatives) with the tool itself. **A default never reaches a tool-saved fixture:** Archi omits `textAlignment="2"` when it saves, so the "written as the default" branch of a rule could only run in an inline model, and #123's had none. **An explanation of another tool's behaviour is a predicate too, on the values it produced, not on the field name.** #139's oracle explained *any* text-alignment difference as "the format cannot carry it". But Archi gives an untold field its own default, so only that value is explained: a group came back left, an element centred, and anything else would have been waved through. The font-name explanation likewise fired on nodes that never had a font. Break each explanation with a value the tool could not have produced, and check that it stays unexplained. **When the tool decides by class hierarchy, derive the table from its metamodel, not from our catalogue's grouping:** Archi ranks legend entries by `isSuperTypeOf` over `archimate.ecore`, where Material is a `TechnologyObject`, so it sorts with technology; our `layer: 'physical'` put it after Equipment (#187). Check every type, not the examples.
- **Mutually exclusive state has one setter, and every path goes through it.** When a PR adds state that must exclude existing state (a selected line against selected shapes), grep every setter of the old state. #142 cleared the line in `choose()`, while the model tree's `?element=` effect called `setSelection` directly, so a line stayed selected under a selected shape, and Delete removed the line. Better still is one state that cannot hold both. **A flag that every edit path must set is set in the function they all call, not at each entry point.** #144's `auto.current = false` ("an edit never makes the view jump") was set by the pointer press and by the drop, but not by the keyboard placement, so placing from the palette re-fit the view.
- **A confirmation names everything the command it confirms does, and every consumer of a command's shape is a caller.** When a cascade grows (#222 taught `removalCommands` the plan cascade), every dialog that previews it, and the history's `describeCommand`, must be updated, and a test asserts the wording for the new subject at *each* call site. #223's fact-sheet Delete removed a rollout's five waves and said only "with its 5 relationships"; after the fix, a zeroed summary on the canvas call site still left every test green, and history still said "6 changes".
- **A freshness check holds what the dry run read, not only what it writes.** For each kind of element a dry run looks up, delete it between preview and apply, and apply: #224's stale check compared only the objects it would change, so a wave or parent deleted after the preview let the import write a dangling reference. **A docblock's guarantee is a criterion:** that check's promise was a sentence in the docblock and the README, and nothing tested it.
- **A refusal or empty-state message must be true on every path that reaches it, and sometimes only an unusual path can.** List the paths. #142's empty connect menu said "ArchiMate allows no relationship from Junction to Business Object", but Association joins anything, so only the junction rules could empty it, and the matrix allowed three types there: the message was false every time it showed. **A shared dialog reused from a new call site is a new path:** read its wording from the new screen. #197 reused the canvas's delete dialog on the fact sheet, where "Also drawn in" and "No other view draws it." have no current view to refer to, and the e2e journey's own unused element was told no *other* view draws it.
- **A summary message over a tally must be true for every key that can reach it, and "a value the format does not allow" means the schema's range, not just "not a number".** List the keys a tally can receive, then read the sentence against each. #112's `exchange.value-malformed` said every colour value "was read as not set", but a malformed opacity keeps its colour, opaque. The same message claimed values the format does not allow, while `r="300"` and `a="150"` were clamped silently: the guard checked parseability, and the XSD's ranges were never consulted.

- **For a format with an implementer's notes document, read the note for each type the writer emits, not only the standard.** [MS-OI29500] records per section what Office writes and accepts: #216 wrote a carriage return as `&#13;` where the note says Office escapes it as `_x000D_`, and the same page settled the author's single-pass `_x005F_` decoding.

For architectural changes, check conformance with `design/decisions/` ADRs; a deliberate deviation needs a new/amended ADR in the same PR, not a silent drift. **A validator message that keeps a dangling record "so it can be reassigned or removed" is a claim about the commands: run each one on the subject the guard kept** (#217's `assignSites` refused the site `validate()` promised could be reassigned, because its Location check applied to sites already in the plan). **When a PR implements an ADR, read every numbered point of the ADR against the diff, and grep the PR's own docs for the ADR's number:** #217 labelled a mapping table "ADR 0013 point 10" while leaving out the Plateau that point requires, and listed the deviation nowhere.

## 3. Code review (the generic layer)

Run the built-in `code-review` skill on the PR at the requested effort level. Verify findings against the actual code before reporting — no speculative findings.

**A finding can name a real code smell and still have an unreachable failure scenario, so check the call sites before you check the logic.** Two from the #24 re-review, both true about the code and wrong about the consequence: *"`removeWorkspace` discards the open workspace's unsaved edits when you delete a different one"* — the only caller passes `store.id`, so it is a latent API hazard, not data loss; *"the leaked `URL` stub breaks every remaining test in the file"* — forcing an early failure left 11/11 passing, because nothing later constructs a `URL`. `git grep` for the callers of the function in the finding, and where the claim is about test fallout, **break it and run the file**. Demote what survives only in principle, and say so in the review — "we checked and it isn't real" is worth as much to the author as a finding, and it stops the next reviewer re-deriving it.

**Check whether the finding is this PR's.** `git diff <base>...<head> -- <file>` on the specific function decides it. #24's proven `propertyTypes` loss lived in `snapshot()`, which the PR never touched — it belonged to `main` and became a new issue, not a change request. A pre-existing bug the PR *makes reachable* is still worth reporting; just report it as what it is.

## 4. Report on the PR

Post one review via `gh pr review <n>` (`--approve` / `--request-changes`, body in markdown) containing:

1. **Acceptance criteria table** (criterion → verdict).
2. **Findings**, most severe first, each with `file:line` and a concrete failure scenario.
3. **Verdict** and, for request-changes, the minimal set of blocking items (nice-to-haves marked as such).

Use inline comments (`gh api` review comments) only where a finding is precisely located and the inline placement helps.

## 5. Harvest rules (the improvement loop — never skip)

For each confirmed finding ask: **would a rule have prevented this?** Escalate to the strongest enforceable tier:

1. **Mechanical** (best): ESLint rule / tsconfig flag / CI check / required test. Add it in the same session — as a commit on the PR branch if trivial, otherwise as a labeled `harness` issue.
2. **Textual**: one added or *sharpened* line in CLAUDE.md "Critical conventions". Keep CLAUDE.md under ~150 lines — replace weaker lines rather than appending forever.
3. **Review-only**: a new bullet in §2 of this skill.

End the PR review body with a `**Harvested:**` line listing what was promoted (or `nothing — findings were one-offs`), so the loop stays visible and auditable.
